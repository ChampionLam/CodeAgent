# 代码阅读与改造

一句话：**没读过的代码不改**。凭函数名猜内部行为是事故的头号来源。

## 步骤

1. **先定位，不猜形状**。用 `search_files` 找到符号的定义处和所有引用处；用 `read_file` 读定义所在的整个函数（不是只读匹配到的那几行）。不知道项目依赖时，先看 package.json / pyproject.toml / go.mod 再断言"这个库有这个 API"。
2. **读上下文**。改动点前后各读一段：调用方传什么参数、返回值被谁消费、有没有兄弟调用路径也在做同一件事（有就在心里记下，第 5 步要查）。
3. **最小改动面**。只改任务要求的逻辑；不顺手重命名、不重排版、不动相邻代码。缺的 import/依赖补上，但新依赖先确认项目里是否已有同类。
4. **匹配项目风格**。命名、缩进、注释语言、错误处理方式都照抄邻近代码；仓库里有 AGENTS.md / CLAUDE.md / .cursorrules 就以它为准。
5. **自查同类缺陷**。修 bug 时查一下兄弟调用路径有没有同样的坑——修一类，不是修一处。
6. **能跑就跑**。用 `run_shell` 跑相关测试/构建；测试挂了先修，修不动就停下来报告 traceback 和卡点，不要带着红测试往下走。
7. 交差时用 `路径:行号` 指回改动点，别整文件贴出来。

## 出岔子的时候

- 同一处补丁连续两次打不上：重读文件拿最新内容再试；第三次别再试，重写整个函数。
- 类型/静态检查报错，修三次仍不过：停下来向用户说明，不要循环死磕。
