## 1. 参照 Hermes 归纳的设计事实（本节表格是对其公开实现的调研结论，落地时按本项目工具面重新实现）

| 点 | Hermes 的做法 | 证据 |
|---|---|---|
| 并发上限 | 读配置 `delegation.max_concurrent_children`，下限 1，默认 10，>10 会警告 | `delegate_tool.py::_get_max_concurrent_children` |
| 深度 | **扁平**：父 → 子，子代理不许再生子代理（MAX_DEPTH=1） | 同上文件 |
| 子代理禁用 | 不能调 `delegate_task` / `clarify` / `memory` / `cronjob` | `delegate_tool.py:4992`（工具描述原文） |
| 派发语义 | 一次性派一批任务，**立刻返回句柄**，不阻塞主对话；结果**合并成一条消息**回到会话 | 工具描述原文 |
| 中断 | 中断单个子代理时**部分结果照样返回** | `delegate_tool.py:5169` |
| 超时 | `DELEGATION_CHILD_TIMEOUT_SECONDS` 环境变量 / `DEFAULT_CHILD_TIMEOUT`，**默认 None（不设硬超时）** | `delegate_tool.py:1019/1167` |
| 可观测 | 子代理有独立 transcript 文件（`delegation_live_log.py`），主端可 list/steer/stop（`subagent.interrupt` RPC） | 源码目录 |

## 2. desk-agent 的落地规格（v1）

### 2.1 工具

新增一个工具 `delegate`，形状参照 Hermes Agent 的 `delegate_task`：

```json
{
  "tasks": [
    {"goal": "…", "context": "…", "output_schema": {…}}
  ],
  "model": "（可选）子代理用什么模型，默认跟本会话一致"
}
```

- 一次最多 3 个任务（`tasks` 长度 > 3 → 直接拒绝，报 `TOO_MANY_TASKS`，不排队静默截断）。
- 返回**立刻**：给每个节点一个 id（`sa-1` / `sa-2` / `sa-3`）和一句话「已派发，做完自动回来」。
  主对话继续，**不阻塞**（这是和现状最大的差别：现在工具是同步等结果）。

### 2.2 并发与调度

- 上限读 `config.json` 的 `delegation.max_concurrent_children`，**desk-agent 默认写 3**（下限 1，上限 3，超过 3 记一条 warn 并按 3 走）。
- 每个节点一个**线程**跑自己的 agent 循环（独立 message 历史、独立工具循环），主循环不受影响。
- 节点数 = 同时跑的子代理数；用完即释放，不做常驻 worker 池（v1 够用）。
- 深度 = 1：子代理的 schema 里**不注入 `delegate`**，它想派也派不了（更稳的做法是直接不进 schema，而不是靠运行时拒绝）。

### 2.3 子代理禁止项（参照 Hermes Agent）

子代理的 tools 列表里去掉：`delegate`、需要用户交互的工具（审批类，一律自动 `deny` 并回一条明确结果，
不许挂住等用户）、写记忆 / 写规则的持久化工具。其余工具正常可用。

### 2.4 结果回灌

- 一批跑完（全部 done / error / interrupted）→ **合并成一条消息**追加到父会话，形如：
  - 每个节点一小节：`✓ sa-1 · goal 一行 · 结果全文（超长按既有截断策略）`
  - 有失败的节点如实标 `✗ sa-2 · 失败原因`，**不许把失败写成成功**。
- 单个节点先做完不单独回灌，等整批（参照 Hermes Agent 的「consolidated message」做法）。

### 2.5 中断与续跑（接现有断点机制）

- 每个子代理**各自有一条运行记录**（复用 `run_checkpoint.py`），`kind=subagent`，带 `parent_run_id`。
- 应用关闭 / 中断 → 节点记 `interrupted`，**保留半截正文**（沿用 `partial` 字段与既定节流：2 秒 / 600 字 / 上限 1500 字）。
- 再启动时，这些中断节点各自出现在「继续」入口里，用户点才续（**不自动接着跑**，用户的既定口径）。
- 硬杀瞬间「正在写的那一下」救不回来 —— 与主循环同一条已知边界。

### 2.6 事件（给界面卡片留口，本轮只发事件不做卡）

`subagent.start` / `subagent.delta`（子代理正文增量）/ `subagent.tool`（子代理调了什么工具）/
`subagent.done` / `subagent.error` / `subagent.batch_done`。
每条事件带 `node_id`、`batch_id`、轮次。阶段 2 的界面卡片直接吃这些事件。

### 2.7 用量记账

子代理的 token 用量按 `subagent:<node_id>` 记进本会话的用量表，父代理自己的用量照旧分开记 ——
这样「谁烧的 token」能查，不是糊涂账。

### 2.8 超时

v1 **不设硬超时**（Hermes Agent 的默认同样是 None）。但要有**无输出看门狗**：单个节点超过 10 分钟没有任何
delta / 工具事件 → 发一条 `subagent.error`（原因写「疑似卡住」）并把该节点标成可续中断，
**不静默吞掉**。

## 3. 明确不做的（v1 范围外）

- 界面卡片（阶段 2）—— 本轮只保证事件流够用。
- steer（用户中途给子代理追加指令）—— 阶段 2 再说。
- 常驻 worker 池 / 跨会话复用子代理。
- 传输层解耦（dispatch 从 stdio 摘出来）—— 另一件事，单独排。

## 4. 验收

- 单测：并发上限（派 4 个 → 同时在跑的最多 3 个）、立刻返回不阻塞、结果合并成一条、
  子代理 schema 里没有 `delegate`、审批类自动 deny、中断后节点可续且带半截正文、
  用量按 `subagent:<id>` 记账。
- 全量测试保持全绿（当前 1052 条）。
- 真机（OpenRouter 免费模型）：派 3 个节点并行抓不同网址，主对话能继续打字，
  整批结果回灌成一条消息。
- **性能指标（2026-09-25 用户新增要求，必须有真实数字，不许靠感觉）**：见 §5。

## 5. 性能 / 内存 / GC（用户新增要求）

### 5.1 风险定性（先说清楚，别自欺）

- **主要风险是 GIL，不是内存。** 3 个子代理 + 主循环在**同一个 Python 进程**里跑线程，
  谁做重 CPU 的活（HTML→MD、大 JSON 解析、文档渲染、OCR 预处理），谁就把别人挤住 ——
  这才是用户体感上的「卡顿」。
- **内存风险有两处**：①子代理的 message 历史 + 工具原文如果不丢引用，跑完一批**只涨不降**；
  ②3 个线程同时写 SQLite（sessions.db）会争锁，可能造成停顿甚至 `database is locked`。
- **GC 风险**：CPython 靠引用计数 + 分代 GC。只要还有引用（比如批次注册表/线程 future 抓着
  子代理的完整历史），对象就不会回收 —— 显式 `gc.collect()` 也救不了，必须**先断引用**。

### 5.2 通过线：绝对预算，与具体机器无关（用户 2026-09-25 纠正）

**底线机型（设计目标，不是当前验证环境）**：4 核 / 8 GB 内存 / 无独显的 Windows 机器；
再往下一档按 **4 GB 可用内存** 处理（降级运行，见 §5.2b）。
**验证环境的资源量不得进任何通过线**（验证环境只是跑通路径用，规格本身不是目标机型）。

| 指标 | 通过线（绝对数，不看具体机器） |
|---|---|
| 空闲基线 sidecar RSS | ≤ 200 MB |
| 3 节点同跑 sidecar 峰值 | **≤ 500 MB 绝对**（8 GB 机上 ≈6%，4 GB 机上 ≈12%） |
| 每节点内存增量 | **≤ 40 MB/节点**（3 节点 ≤ 120 MB 增量） |
| 批次结束回落 | ≤ 峰值 − 60%，且 ≤ 基线 + 60 MB（**必须真回落**） |
| 主循环 RPC 延迟 | p50 ≤ 100 ms、**p95 ≤ 300 ms**、p99 ≤ 1 s（低配机同一根线） |
| 派发延迟（delegate 返回） | ≤ 300 ms |
| 应用总 CPU（3 节点跑时） | ≤ 2 个核（4 核机上不许占满） |
| 线程数 / 句柄 / 对象残留 | 批次结束后回基线，不残留 |
| SQLite 争用 | 无 `database is locked` |

**硬规则：任何阈值不许从「本机总内存 / CPU 数」算出来。** 测试用例里禁止读真实机器的
总内存当参照（那种写法在大内存机器上必然「通过」，掩盖低配问题）。

### 5.2b 低配要降级，不许硬撑

- **有效节点数 = min(3, 按资源档位取整)**：
  - 可用内存 < 4 GB → **1 个节点**
  - 4–8 GB → **2 个节点**
  - ≥ 8 GB → **3 个节点**（上限，用户口径）
  - 再叠加 CPU：`cpu_count // 2` 取小值（4 核 → 2 个节点上限）
- **派发前内存闸门**：sidecar RSS 已 > 500 MB → **拒绝派新节点**，明确回报原因（不静默失败）。
- **运行中内存看门狗**：RSS > 700 MB → 停止接受新节点 + 发通知给用户（照既有 `subagent.error` 事件）。
- 降级是**显式**的：结果里要写清楚「本次只跑 2 个节点，因为可用内存 5.4 GB」，不许悄悄少跑。

### 5.3 测试必须在「模拟低配」下也过

- 测试里**注入** cpu_count / 可用内存（monkeypatch 或环境变量）→ 断言有效节点数按档降级。
- 断言**绝对上限**（RSS ≤ 500 MB 这类），不断言「比当前机器涨了多少」。
- 必须有一条「低配档（4 GB / 2 核）下派 3 个任务 → 实际只跑 1–2 个 + 明确提示 + 主循环 p95 仍达标」的用例。
- 必须有一条「已超内存闸门 → 拒绝派发且原因可见」的用例。

### 5.4 实现上必须遵守的内存纪律

1. 子代理跑完 → **立刻丢引用**：历史、流式缓冲、工具原文都不留在内存；transcript 落盘
   （参照 Hermes Agent 的 live log 做法，本项目用 `run_checkpoint.py` 的运行记录承载），内存里只留最终摘要 + 用量。
2. 大批工具输出沿用既有落盘机制（`sessionstore.append_spilled_output`），不进常驻内存。
3. 整批结束 → **显式 `gc.collect()` 一次**（只允许在批次边界，不许每轮都调），
   并把调用前后 RSS 记进 run 记录（可追溯）。
4. 批次注册表（节点表）在完成 / 中断 / 失败后都要清条目，不许只增不减。
5. 中断的节点：半截正文已落盘 → 内存里那份照样弃掉（以磁盘为准）。
6. 有界并发：最多 3 个在跑；`tasks > 3` 直接拒，**不做无界排队**。
7. 主线程不做重活；若量出重 CPU 的解析/渲染确实拖慢主循环，**挪子进程**——
   先量再决定，不许拍脑袋改。
### 5.5 GIL 实测与修法（2026-09-26，实测记录）

5.4 第 7 条写的「先量再动」已经量完，结论是 **护航效应（convoy effect）**，不是内存问题——
三个纯 CPU 子代理线程会把主循环饿到零采样：

| 场景（3 个纯 Python 自旋子代理线程） | 主循环采样/0.8s | p50 | p95 | dispatch |
|---|---|---|---|---|
| GIL 切换间隔 5ms（Python 默认），8 核机 | 7 | 117.4ms | **744.4ms** | — |
| 间隔压到 1ms | 43 | 11.1ms | 84.8ms | — |
| 间隔压到 0.5ms | 84 | 8.4ms | 24.6ms | — |
| 修前仓库用例（引擎级） | **0** | nan | nan | 1217.4ms |
| 修后（8 核） | 95 | 2.1ms | 8.8ms | 37.6ms |
| 修后（taskset 0-3，模拟 4 核最低配） | 95 | 2.8ms | 8.2ms | 25.7ms |

修法：`python/subagent.py` 加 **GIL 租约** —— 节点活着时 `sys.setswitchinterval(0.0005)`，
最后一个节点结束时还原（全局计数，多批次安全），常量 `NODE_SWITCH_INTERVAL_S`。
先跑的独立微基准（三档间隔对照）确认机制成立，才动仓库代码，没有先改实现再找理由。

注：这是**纯 CPU** 子代理的病态场景；真实节点大量时间在等 LLM API（I/O，会释放 GIL），
常规负载下 p95 是个位数毫秒。4 核机同一根线不放松（上表最后一行）。
子进程方案（5.4.7）保留为「节点真做重 CPU 活」时的后备，当前数据不支持必须先上子进程。
